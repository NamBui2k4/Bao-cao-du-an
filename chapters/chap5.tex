\chapter{Experimental results and analysis}

In this chapter, the performance metrics of both Monolithic and Microservice architectures are evaluated 
through a series of controlled experiments. The goal is to quantify the differences in efficiency, stability, 
and resource consumption under varying load conditions.

\section{Analysis of Throughput \& Response Time}

This section evaluates the performance of both Monolithic and Microservice architectures through two primary 
metrics: Throughput (requests per second, RPS) and Response Time (average latency in milliseconds). Load generation 
was performed using k6, simulating a complete user journey comprising four sequential 
API calls — GET /courses, GET /courses/:id, POST /login, and POST /enrollment — with a 1-second 
think time between cycles. All tests were executed across two distinct scenarios to capture both 
gradual scaling behavior and peak burst resilience.

\subsection{Scenario 1: Gradual Ramp-Up Load}

In the first scenario, the number of Virtual Users (VUs) was increased incrementally from 1 to 2,000 across twelve discrete levels (1, 5, 10, 15, 20, 50, 100, 200, 500, 1,000, 1,500, and 2,000 VUs), with each level sustained for a fixed duration before advancing. This approach mirrors realistic LMS usage patterns such as the progressive influx of students accessing course materials at the start of a semester.

\begin{figure}[H]
\centering
\includegraphics[width=1\textwidth]{images/my-demo/charts/throughput&response/ramp/throughput.png}
\caption{Throughput Comparison under Gradual Ramp-Up Load (Scenario 1)}
\label{fig:throughput_s1}
\end{figure}

At low and moderate load levels (1–100 VUs), the Monolithic architecture sustains a measurably higher throughput. At 50 VUs, Monolith achieves 48.33 RPS versus 47.00 RPS for Microservice — a modest but consistent advantage attributable to the elimination of inter-service network hops. Internal module communication via direct function calls within a single process incurs zero network latency, whereas every Microservice request must traverse the Nginx API Gateway before reaching the target service.

A critical crossover occurs at approximately 1,000 VUs. At this threshold, Monolith throughput begins to plateau at around 390–435 RPS while Microservice continues to scale, reaching 579.17 RPS at 2,000 VUs compared to 430.94 RPS for Monolith. This reversal reflects a structural bottleneck in the Monolithic architecture: as concurrent connections accumulate, the shared Node.js event loop and single database connection pool become contention points, throttling effective throughput. Microservice, by contrast, distributes request handling across independently-deployed services (Account, Academic, Course), each maintaining its own connection pool and processing queue.

The response time degradation curve for the ramp-up scenario further illuminates the saturation mechanism. At 200 VUs, the Monolith's average response time of 133.4 ms remains within acceptable user experience bounds (typically defined as sub-200 ms for interactive web applications). However, the P99 response time at this load level already exceeds 800 ms — indicating that while the average user experience remains acceptable, a statistically significant minority of requests are experiencing severe queue starvation. This divergence between mean and P99 is a characteristic signature of event-loop saturation in single-threaded Node.js applications: the majority of requests are processed quickly when the event loop is available, but requests that arrive during database I/O wait cycles are queued and incur disproportionate latency.

The Microservice P99 behavior at 200–500 VUs tells a different story. The P99 value of 30,002 ms — effectively the 30-second timeout boundary imposed by the k6 test configuration — indicates that a small but non-trivial proportion of enrollment requests are being dropped entirely rather than served with degraded latency. This behavior reflects the cross-service coordination chain: a POST /enrollment request that arrives at AccountService while the service's connection pool is exhausted will wait for a connection; if the wait exceeds the downstream service timeout, the entire multi-step transaction fails. The architectural implication is that the Microservice write path introduces a failure mode — partial transaction timeout — that is structurally absent in the Monolith, where the entire write operation executes within a single memory space with deterministic connection pool access.

\begin{figure}[H]
\centering
\includegraphics[width=1\textwidth]{images/my-demo/charts/throughput&response/ramp/response.png}
\caption{Response Time Comparison under Gradual Ramp-Up Load (Scenario 1)}
\label{fig:response_s1}
\end{figure}

Regarding response time, at low concurrency (1–20 VUs), Monolith maintains a significantly lower average response time — 12.8 ms at 1 VU compared to 34.1 ms for Microservice. This gap originates from the serialized inter-service path that each Microservice request must traverse: authentication via Account Service, enrollment validation through Academic Service, and course data retrieval from Course Service. Each network hop and JSON serialization/deserialization cycle contributes cumulative latency that is absent in the Monolithic process model.

However, as load escalates beyond 200 VUs, the performance relationship inverts. At 500 VUs, Monolith average response time reaches 213.2 ms while Microservice experiences severe degradation at 1,296.6 ms — a reflection of queue saturation in the write-heavy enrollment pathway. Notably, at 1,500–2,000 VUs, Microservice stabilizes at 1,205–1,557 ms while Monolith continues to climb to 1,847 ms, confirming that distributed processing capacity ultimately absorbs sustained high-concurrency load more effectively.

\subsection{Scenario 2: Peak Load (Flash Crowd Simulation)}

The second scenario simulates worst-case peak conditions — analogous to hundreds of students simultaneously submitting assignments moments before a deadline — by injecting all VUs simultaneously with zero ramp-up time. Six load levels were tested: 10, 100, 500, 1,000, 1,500, and 2,000 VUs.

\begin{figure}[H]
\centering
\includegraphics[width=1\textwidth]{images/my-demo/charts/throughput&response/concurrent/throughput.png}
\caption{Throughput under Simultaneous Peak Load (Scenario 2)}
\label{fig:throughput_s2}
\end{figure}

Under burst conditions, the two architectures exhibit dramatically different scaling curves. At 10 VUs, both architectures 
deliver comparable throughput (Monolith: 19.13 RPS, Microservice: 18.54 RPS), confirming that at minimal load the 
network overhead of Microservice is not yet consequential. However, as burst load intensifies, Microservice begins 
to assert a substantial throughput advantage: at 1,000 VUs, Microservice processes 1,694.78 RPS versus 764.29 RPS
for Monolith. At 1,500 VUs, Microservice reaches 5,318.77 RPS compared to 3,258.60 RPS for Monolith — a 63\% advantage. 
At peak 2,000 VUs, Microservice achieves 6,593.21 RPS while Monolith delivers 5,548.00 RPS.

This behavior confirms that Microservice' distributed processing model provides superior parallelism under sudden high concurrency. When 2,000 requests arrive simultaneously, the Monolithic single-process event loop queues requests sequentially, whereas Microservice containers handle requests in parallel across multiple isolated processes.

\begin{figure}[H]
\centering
\includegraphics[width=1\textwidth]{images/my-demo/charts/throughput&response/concurrent/response.png}
\caption{Response Time under Simultaneous Peak Load (Scenario 2)}
\label{fig:response_s2}
\end{figure}

The response time data for this scenario reveals a notable pattern reversal compared to Scenario 1. At 10 VUs, Monolith exhibits lower average latency (21.1 ms versus 38.7 ms for Microservice), consistent with the absence of inter-service hops. However, as load escalates to 500 VUs, Microservice response time spikes sharply to approximately 2,089 ms — significantly higher than Monolith's 669.7 ms at the same load level. This spike reflects the compounding effect of inter-service coordination under simultaneous burst pressure: each request must sequentially acquire tokens from Account Service and validate enrollment through Academic Service before completing.

The trajectory reverses dramatically at 1,000 VUs and beyond. Microservice response time 
falls to 501.3 ms at 1,000 VUs and further to 68.0 ms at 2,000 VUs — a counter-intuitive improvement 
explained by the system reaching full parallelism saturation, with all service containers actively 
processing requests simultaneously. Monolith response time at 2,000 VUs remains at 203.7 ms, constrained 
by the centralized event loop. 

This 30.7-fold improvement in Microservice response time — from 2,089 ms at 500 VUs to 68.0 ms at 2,000 VUs — is not a measurement artifact but reflects the saturation-induced parallelism recovery mechanism characteristic of distributed container architectures. At 500 VUs, the system has accumulated sufficient concurrent requests to saturate the sequential coordination chain (AccountService token validation → AcademicService enrollment verification) but has not yet reached the threshold at which all containers are simultaneously active. This intermediate state produces maximum queue depth and worst-case wait time. As load crosses 1,000 VUs and all service containers enter sustained full utilization, inter-container request queues stabilize and the effective per-request latency converges toward the service's minimum processing time rather than the queue's maximum wait time. The Monolith does not exhibit this recovery behavior because its single event loop has no equivalent parallel saturation mechanism — once the callback queue is full, each additional request increments wait time linearly regardless of total load.

This divergence indicates that under extreme concurrent burst conditions, 
the Microservice architecture delivers substantially better per-request latency for individual users despite
 its higher infrastructure overhead.


\section{Analysis of CPU Usage}

This section evaluates CPU resource consumption across both architectures using an incremental load methodology adapted from Schlögl et al. (2024). Resource telemetry was captured via docker stats at five-second polling intervals and processed into time-series visualizations. Three test cases are examined, each representing a progressively more demanding operational scenario: read-only access, write-intensive access, and high-concurrency mixed load.

To characterize resource scaling behavior, each architecture was subjected to twelve discrete user load levels (1, 5, 10, 15, 20, 50, 100, 200, 500, 1,000, 1,500, and 2,000 VUs) under ramp-up conditions, with CPU consumption recorded at each level. This approach yields a complete picture of how resource utilization evolves from idle baseline through saturation, enabling precise identification of the load threshold at which architectural differences become operationally significant.

\subsection{Scenario 1: Read-Only Access (GET /courses)}
This scenario simulates the most common LMS interaction pattern: unauthenticated browsing of the course catalog via GET /courses. This lightweight read scenario isolates baseline infrastructure overhead from business logic processing costs.

\begin{figure}[H]
\centering
\includegraphics[width=1\textwidth]{images/my-demo/charts/cpu_usage/tc1/cpu_vu.png}
\caption{Average CPU Usage across Load Levels — TC1 Read-Only (Monolith vs. Microservice)}
\label{fig:cpu_s1_avg}
\end{figure}

Analysis of CPU consumption shows a notable behavioral divergence at low load. At 1–15 VUs, both architectures exhibit CPU consumption in the 33–44\% range — however, Microservice demonstrates more volatile fluctuation, peaking at 48\% at 100 VUs before falling back to 36\% at 200–500 VUs, while Monolith sustains a steadier rise from 38\% to 52\% across the same range. At 1,000–2,000 VUs, the trajectories converge and rise in parallel, with Monolith reaching 69.2% and Microservice reaching 63.8% at 2,000 VUs.

The early-stage CPU volatility in Microservice is attributable to RabbitMQ burst activity visible in the per-container timeline: even under a simple GET /courses request, the message broker incurs periodic CPU spikes as it processes heartbeat and topology synchronization frames — overhead entirely absent in the Monolithic process model.

\begin{figure}[H]
\centering
\includegraphics[width=1\textwidth]{images/my-demo/charts/cpu_usage/tc1/cpu_time_mono.png}
\caption{CPU Usage Timeline — Monolith, 1 VU (Read-Only)}
\label{fig:cpu_s1_mono}
\end{figure}

In the Monolithic timeline, CPU consumption follows a "burst-and-rest" pattern, where the container spikes during request processing and returns to near 0\% during idle periods. The total host CPU consumption (host\_total) ranges between 40\% and 90\%, indicating that at low loads, the application's actual resource footprint is negligible compared to the background noise of the operating system and Docker engine.

\begin{figure}[H]
\centering
\includegraphics[width=1\textwidth]{images/my-demo/charts/cpu_usage/tc1/cpu_time_micro.png}
\caption{CPU Usage Timeline — Microservice, 1 VU (Read-Only)}
\label{fig:cpu_s1_micro}
\end{figure}

In contrast, Microservice reveal the structural overhead of a distributed architecture. The RabbitMQ container consumes a consistent 40–60\% CPU even when idle due to the Erlang VM's constant polling and scheduling mechanisms. Other service containers also maintain higher baseline activity to manage connection pools and health checks. This "infrastructure tax" confirms that Microservice require a significant minimum resource threshold regardless of actual application load.

\subsection{Scenario 2: Write-Intensive Access (POST /profile)}
This scenario introduces database write operations via POST /profile, which requires input validation, database record creation, and response serialization. This scenario examines how each architecture handles CPU pressure from concurrent write workloads.

\begin{figure}[H]
\centering
\includegraphics[width=1\textwidth]{images/my-demo/charts/cpu_usage/tc2/cpu_vu.png}
\caption{Average CPU Usage across Load Levels — TC2 Write-Intensive (Monolith vs. Microservice)}
\label{fig:cpu_s2_avg}
\end{figure}

Monolith CPU climbs steeply from 40.5\% at 1 VU to a peak of 69.2\% at 2,000 VUs, following a consistent upward trajectory. The Microservice curve, however, displays a pronounced dip to 36.4\% at 200–500 VUs before recovering to 63.8\% at 2,000 VUs. This dip reflects the write timeout behavior observed in the raw data: at 200–500 VUs, Microservice write requests begin timing out at 30 seconds, drastically reducing the effective number of active requests being processed and thus suppressing measured CPU consumption despite the high user count.

This finding has important implications: the Microservice write path under ramp conditions suffers from cross-service coordination overhead that causes response time to exceed 30 seconds at 200–500 VUs (p99 = 30,002 ms), indicating that the distributed transaction across Account Service and Academic Service creates a cascading latency chain under moderate sustained write load. Monolith, processing all write operations within a single memory space, avoids this coordination cost.

\subsection{Scenario 3: Mixed Concurrent Load}

The final scenario represents the most demanding scenario: 2,000 VUs injected simultaneously with 
a mixed workload combining GET /courses, GET /profile, POST /profile, and POST /enrollment requests. 
The objective is to observe CPU behavior at the system's operational ceiling and identify 
architectural resilience characteristics.

\begin{figure}[H]
\centering
\includegraphics[width=1\textwidth]{images/my-demo/charts/cpu_usage/tc3/cpu_vu.png}
\caption{Average CPU Usage across Load Levels — TC3 Mixed Concurrent Load (Monolith vs. Microservice)}
\label{fig:cpu_s3_vu}
\end{figure}

Analysis of aggregate CPU levels shows that, under mixed load, Microservice always maintains higher aggregate 
CPU than Monolithic at all load levels. At 100 VU, Microservice reached 54.4\% compared to 36.0\% for 
Monolith. At 1,000 VU, the gap widens further: Microservice is at 74.0\% compared to Monolith's 48.7\%. At 1,500 VU, Microservice 
peaked at 88.1\% while Monolith reached 62.9\%. The two architectures converge somewhat at 2,000 VU — 
Microservice at 84.5\% and Monolith at 72.4\% — as both systems approach resource saturation


Critically, the higher aggregate CPU cost of Microservice under mixed 
load does not translate into a performance penalty. At 2,000 VUs, 
Microservice delivers 6,593 RPS versus 5,548 RPS for the Monolith — 
a 19.0\% throughput advantage — while simultaneously maintaining a 
substantially lower average response time (68 ms versus 204 ms). This 
counter-intuitive result — greater CPU expenditure yielding superior 
throughput and lower latency — is explained by the architecture's 
distributed concurrency model: multiple containers process read and 
write requests in parallel across isolated pipelines, whereas the 
Monolith serializes all request types through a single event loop. The 
defining trade-off of Microservice at scale is therefore not raw CPU 
economy but output per unit of CPU consumed, as quantified by the 
RUE\_CPU analysis in Section 6.4.



\begin{figure}[H]
\centering
\includegraphics[width=1\textwidth]{images/my-demo/charts/cpu_usage/tc3/cpu_time_mono.png}
\caption{CPU Usage Timeline — Monolith, 2,000 VUs (Mixed Load)}
\label{fig:cpu_s3_mono}
\end{figure}

At 2,000 VUs, the Monolith reaches full saturation with the backend container consuming 130–185\% CPU. Because there is no resource isolation, all read and write requests compete for the same single-process resources, creating a global bottleneck. A surge in heavy write tasks directly degrades the response time of concurrent read tasks. This lack of resource partitioning is a fundamental architectural limit that prevents the Monolith from scaling throughput further even if host resources are available.

\begin{figure}[H]
\centering
\includegraphics[width=1\textwidth]{images/my-demo/charts/cpu_usage/tc3/cpu_time_micro.png}
\caption{CPU Usage Timeline — Microservice, 2,000 VUs (Mixed Load)}
\label{fig:cpu_s3_micro}
\end{figure}

The Microservice architecture presents a drastically different picture characterized 
by clear resource differentiation. While the Account Service and RabbitMQ absorb the 
brunt of the write workload with spikes up to 200–540\%, the Course Service and API 
Gateway remain stable at very low levels (under 25\%). This isolation ensures that users 
browsing courses remain completely unaffected by the saturation of enrollment services. 
By localizing saturation to specific services, Microservice prevent system-wide failure 
and maintain a consistent user experience across unrelated functional domains. This fault 
and resource isolation is the most significant operational advantage of Microservice for
LMS platforms with uneven load distributions.

\section{Fault Tolerance Analysis}
This section evaluates the structural resilience of both architectures by analyzing their behavior during the development and integration lifecycle. By utilizing empirical data from the project's commit history, the analysis moves beyond theoretical availability formulas to examine how the "Blast Radius" of common configuration and deployment errors differs between a unified monolithic core and a decoupled Microservice ecosystem. This practical investigation provides a granular look at the trade-off between configuration complexity and system-level robustness.

The commit data we recorded from April 2nd 2026 to May 6th 2026, which is contained in two .xlsx file  of \texttt{commit\_history/}. One of them belongs to microservice log and the other belongs to monolithic. Each file shows a clear difference in the scope of impact when errors occur. 
Specifically, in monolithic systems, errors such as "missing dist folder" (April 29) or "Incorrect build context" resulted in a full-blown fail. The entire system failed to launch due to the tight dependency on a single Dockerfile. Meanwhile, Microservice exhibited
configuration errors such as "incorrect path matching" at Nginx (May 1) and only caused localized failures for a specific service. History shows that other services (such as AccountService) 
remained healthy and functioned normally, demonstrating the ability to isolate the risk. Additionally, history records several commits related to RabbitMQ tweaks. However, these issues did not cause a chain reaction of failures. The separation of the database helps Microservice avoid the widespread database connection timeout errors often seen in Monolithic 
architectures when a module consumes all connection pool resources.

In our experience, team assign $t^{limit}=2 \ hours = 7200 \ second$. This interval is the 
shortest and most ideal time period for exception operations not related to system development

    \caption{Performance Statistics — Microservice Architecture}
    \label{fig:response time of microservice in first scenario}
\end{figure}

Although Microservice have a higher number of failed commits, their tolerance is better than monolithic, 
as shown by the availability index. Thanks to independent encapsulation, errors are localized. The system 
accepts the failure of a small service to protect the overall availability.

The evaluation of fault tolerance in this study is further enriched by an analysis of the 
development phase, reflecting the practical experiences of the developers. This analysis is 
grounded in the commit history 
recorded in microservice\_commit\_history.xlsx and monolithic\_commit\_history.xlsx, which document events, error codes, locations of occurrence, and the underlying causes of failures encountered during the implementation of both architectures.

A critical observation regarding fault isolation emerges when examining the scope of impact for various errors. In the Monolithic architecture, specific events such as a \textit{"missing dist folder"} or an \textit{"incorrect build context"} (e.g., recorded at 20:43:22 on April 29) caused the entire build and deployment process to collapse. Because the Monolith exists as a single unified unit, a flaw in the \texttt{Dockerfile} or a missing library in \texttt{package.json} paralyzes all functionalities, from authentication to course management. Conversely, the Microservice architecture demonstrated superior operational tolerance. For instance, an \textit{"incorrect path matching"} error at the Nginx gateway (occurring at 09:44:14 on May 01) only resulted in a localized failure for the Academic service endpoints. Other components, such as the \texttt{AccountService}, remained fully functional and were successfully deployed as evidenced by previous stable commits. This confirms that in a Microservice ecosystem, a mistake in one module does not necessarily cripple the entire deployment of other independent modules.

However, the recovery process introduces a different perspective on complexity. Based on the calculated Mean Time to Recovery (MTTR), the Microservice architecture exhibited significant delays between failure detection and resolution. A notable example involved a 40-minute struggle to fix incorrect port mappings and frontend-gateway paths. The challenge of managing numerous ports and inter-service routes in a massive \texttt{docker-compose} environment proved to be a significant hurdle for the team. The debugging process becomes inherently slower when navigating the distributed nature of the system. In contrast, the Monolithic architecture, which lacks such granular division of ports and paths, proved to be much easier to debug, leading to the conclusion that while Microservice are more resilient, Monoliths are more maintainable during the initial debugging phases.

Infrastructure resilience also showed distinct patterns between the two architectures. During the development of the Microservice version, the team experienced a "trial and error" phase where services frequently fluctuated between \textit{healthy} and \textit{unhealthy} states. Crucially, once a service like the \texttt{AccountService} reached long-term stability, it became an independent anchor, allowing developers to modify other services like \texttt{CourseService} without any risk of side effects. This independence was absent in the Monolithic version, where shared resources like the database meant that a local error often escalated into a global system failure, frequently observed in Docker logs as repetitive database or build errors.

While it may seem contradictory that Microservice had a higher number of failed commits despite being more "stable," this was primarily due to human error rather than architectural flaws. Many failures resulted from simple typos in Nginx or RabbitMQ configurations that, due to the distributed nature of the system, took considerable time to trace—sometimes up to 20 minutes—using Docker logs and health checks. Ultimately, the 148 recorded commits suggest that while the Monolithic architecture is simpler to configure, its failures are total and comprehensive. Microservice, despite requiring more configuration effort, provide the essential advantage of partial operation, minimizing the "blast radius" of errors during the development lifecycle.

Therefore, the Microservice architecture demonstrates superior tolerance by converting system crashes into partial failures, 
thereby ensuring the system's robustness throughout development and actual operation.

\section{Cost Efficiency Analysis}

By applying the Resource Utilization Efficiency (RUE) framework, the analysis shifts from raw performance metrics to a "Performance-to-Cost" perspective, identifying the specific workload thresholds where each architectural model becomes the more financially sustainable choice for an LMS deployment.

The Resource Utilization Efficiency (RUE) is a critical metric in this study, as it defines the economic and operational feasibility of each architecture. Based on the telemetry captured during the 2,000 VU stress tests, the following analytical points clarify the performance-to-resource ratio.

The testing environment was strictly controlled to eliminate background 
processes that could interfere with resource consumption.
We utilize \textbf{k6} to simulate user traffic across three scenarios:

\begin{itemize}

    \item \textbf{Idle load:}  This is the simplest scenario, the architectures do not handle any requests for 5 minutes. 
    In this scenario, we are only interested in the cost that an architecture must pay to stay ready.

    \item \textbf{Normal Load:} Simulating 200 Virtual Users (VUs) sending continuous requests 
    to the \textbf{/api/v1/health} endpoint for 5 minutes to determine standard operational costs.

    \item \textbf{Peak Load:} Stressing the system with 1000 VUs to observe 
    resource isolation and maximum capacity limits.
\end{itemize}

Also, the \texttt{docker stats} command and automated scripts captured the 
average resource consumption during each interval.

\subsubsection{\textbf{Idle Load (Cost of Readiness)}}

The Idle Load scenario represents the baseline cost that each architecture must incur to remain operational and ready to serve requests, even when no user traffic is present. This is also known as ``Cost of Readiness'' or ``Static Cost'' -- an important aspect in cost-efficiency analysis because cloud providers charge for resources regardless of actual utilization.

In this scenario, both architectures ran for 5 minutes without any incoming requests. We measured only the background resource consumption required to keep all containers and services in a healthy, ready state.

As shown in Table \ref{tab:resource_summary_idle}, the results reveal a notable difference in baseline memory footprint:

\begin{table}[h]
\centering
\caption{Baseline Resource Consumption under Idle Load}
\label{tab:resource_summary_idle}
\begin{tabular}{|l|c|c|}
\hline
\textbf{Architecture} & \textbf{Avg CPU (\%)} & \textbf{Avg RAM (MiB)} \\ \hline
Microservice         & 1.35\%                & 326.55                 \\ \hline
Monolithic            & 1.54\%                & 433.64                 \\ \hline
\end{tabular}
\end{table}

The Microservice architecture demonstrates superior cost efficiency in the idle state, consuming approximately \textbf{25\% less RAM} (326.55 MiB compared to 433.64 MiB of the Monolithic architecture). This advantage comes from the modular design where each service runs in a lightweight Alpine-based container and only loads necessary dependencies. In contrast, the monolithic application must load the entire codebase, all modules, and libraries into memory from startup, resulting in a higher baseline memory footprint.

This finding challenges the common assumption that Microservice always consume more resources due to multiple containers. In reality, with proper optimization (such as using Alpine Linux images and minimal service footprints), Microservice can achieve better ``Cost of Readiness'' than a monolithic application.

Since there are no processed requests in the Idle scenario (\(N = 0\)), the traditional RUE formula cannot be applied. Instead, we evaluate efficiency through direct comparison of baseline resource consumption, highlighting the static cost each architecture must pay to maintain system availability.

In contrast, the \textbf{Monolithic} architecture (orange line), while having a

In terms of memory allocation, \textbf{Microservice} proved to be more efficient, utilizing

necessary stability. The unusual spikes on the Monolithic graph indicate that this architecture 
is susceptible to background processes and garbage collection mechanisms. Conversely, Microservice, 
despite having a higher CPU usage due to managing 8 containers, exhibited extremely stable fluctuations.

Substituting these values into the $RUE$ formulas, we derive the following efficiency scores:

\begin{itemize}
    \item \textbf{Microservice:} $RUE_{CPU} \approx 1148.09$ (req/\%) and $RUE_{RAM} \approx 135.45$ (req/MiB).
    \item \textbf{Monolithic:} $RUE_{CPU} \approx 573.22$ (req/\%) and $RUE_{RAM} \approx 27.23$ (req/MiB).
\end{itemize}

The $RUE$ scores index reaching 1148.09 (twice higher than Monolithic's 573.22), which show that Monolithic do not equate to economics. 
This calculation result is completely reasonable because although Monolithic has lower CPU 
consumption (22.33\%), it can only handle 12,802 requests. Meanwhile, Microservice handles 
up to 59,600 requests - 4.65 times more than Monolithic in the same time conditions. Microservice has 
demonstrated the ability to convert resources into outstanding processing output, actually saving more operating costs when 
considered per unit of successful request.

The cost calculus reverses under peak load, however. At 1,000 VUs, the Monolith processes 296,562 requests at a CPU cost of 95.36 units — approximately 1 CPU unit per 3,109 requests — while Microservices processes 266,469 requests at 392.15 CPU units — approximately 1 CPU unit per 679 requests. For cloud deployments where compute costs scale linearly with CPU allocation, the Monolith would incur approximately 4.58 times lower compute cost per successful request during peak periods. Institutions with highly variable traffic profiles — characterized by long periods of moderate load punctuated by short, intense enrollment or examination spikes — therefore face a genuine architectural cost trade-off that cannot be resolved by examining either load regime in isolation.


\subsubsection{\textbf{Peak Load}}

In this scenario, the system was subjected to a peak load of 1,000 Virtual Users (VUs) to determine 
its performance limits. As illustrated in Figure \ref{fig:peak_load_analysis}, the \textbf{Microservice} 
architecture (blue line) experienced extreme CPU volatility, with frequent spikes reaching between 400\% and 600\% utilization. This indicates a massive computational overhead required to manage the complex orchestration and networking between eight different containers. Conversely, the \textbf{Monolithic} architecture (orange line) demonstrated remarkable resilience, maintaining a highly stable CPU profile consistently below 150\% throughout the duration of the test.
