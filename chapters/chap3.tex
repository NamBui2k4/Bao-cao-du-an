\chapter{System Design}

\section{System stakeholders analysis}

The system targets educational institutions requiring comprehensive course management, 
content delivery, and learner tracking capabilities. The following primary stakeholder 
groups are identified based on their roles and interactions with the LMS:

\begin{itemize}
    \item \textbf{Guests:} Unauthenticated visitors who can view public course 
    information and access system registration. Their primary actions are account 
    registration and login. \textit{Example: Minh, a prospective student, browses 
    the course catalog before creating an account to enroll.}
    
    \item \textbf{Students:} Registered learners who enroll in courses, 
    access learning materials, submit assignments, take assessments, and track their 
    progress. They need intuitive navigation, clear progress indicators, and timely 
    notifications for deadlines. \textit{Example: Anh, an engineering student, 
    manages 5 courses simultaneously and relies on the LMS dashboard to stay organized 
    with assignments and exam schedules.}
    
    \item \textbf{Instructors:} Course creators who develop curriculum, 
    upload learning content, create assessments, grade submissions, and monitor 
    student progress. They require robust content authoring tools, efficient grading 
    workflows, and analytics on student performance. \textit{Example: Bình teaches 
    3 courses with 150 students and needs bulk grading features and reusable content 
    templates to manage his workload.}
    
    \item \textbf{Department Heads/Reviewers:} Quality assurance 
    personnel who review and approve course content before publication, ensuring 
    alignment with institutional standards. They inherit all instructor capabilities 
    plus approval workflow management. \textit{Example: Chi reviews 20+ courses per 
    semester, requiring a clear approval queue and structured feedback mechanisms.}
    
    \item \textbf{System Administrators:} Personnel responsible for 
    user account management, role assignments, system configuration, and technical 
    support. They need powerful search/filtering tools, bulk operations, and comprehensive 
    audit logs. \textit{Example: Dũng manages 5,000+ accounts and handles peak loads 
    during enrollment periods.}
    
    \item \textbf{Product Owners:} Institutional stakeholders 
    who define pedagogical objectives, compliance requirements, feature roadmaps, and 
    measure learning outcomes.
\end{itemize}

These stakeholder groups represent distinct user needs that drive both functional 
requirements (course management, assessment, grading) and non-functional requirements 
(performance, security, accessibility, scalability). The personas embedded within each 
group help anchor requirements in realistic educational workflows and justify design 
decisions throughout the development process.

The interaction model between these stakeholders and the system varies significantly depending on the chosen architecture. In the Monolithic design, stakeholder requests are handled by a unified application tier, ensuring low-latency communication between functional modules at the cost of potential process contention. Conversely, the Microservice design introduces a distributed interaction layer where each stakeholder's action may traverse multiple independent services, necessitating a robust API Gateway to maintain a seamless user experience despite the underlying structural complexity.

\section{Detailed Backend Architectures}

\subsection{Monolithic organization}

\subsubsection{Layer decomposition strategy}


The codebase is organized into the following Repository pattern, as illustrated in the directory 
structure:

\begin{itemize}
    \item \textbf{Controllers Layer} (\texttt{/controller}): Handles HTTP request routing and response 
    formatting. Controllers are organized by domain entity (e.g., \texttt{course.controller.ts}, 
    \texttt{student.controller.ts}, \texttt{quiz.controller.ts}) and delegate business logic to 
    service layer components.
    
    \item \textbf{Services Layer} (\texttt{/services}): Implements core business logic and orchestrates 
    repository operations. Service classes are stateless and handle use case workflows such as course 
    enrollment validation, grading calculations, and submission processing.
    
    \item \textbf{Repository Layer} (\texttt{/repository}): Provides data access abstraction using 
    TypeORM repositories. Each repository encapsulates database queries for a specific entity 
    (e.g., \texttt{course.repository.ts}, \texttt{quiz.repository.ts}) and shields business logic 
    from raw SQL operations.
    
    \item \textbf{Entity Layer} (\texttt{/models}): Defines TypeORM entity classes that map to database 
    tables. Entities include \texttt{courses.entity.ts}, \texttt{enrollment.entity.ts}, 
    \texttt{quizzes.entity.ts}, and others corresponding to the ERD defined. Entity relationships 
    (one-to-many, many-to-many) are declared using TypeORM decorators.
    
    \item \textbf{Authentication Module} (\texttt{/auth}): Implements JWT-based authentication using 
    Passport strategies. Includes role-based access control (RBAC) guards (\texttt{roles.guard.ts}) 
    that enforce permissions for Student, Instructor, Reviewer, and Admin roles as defined in the 
    stakeholder analysis.
    
    \item \textbf{View Layer} (\texttt{/views}): Server-side rendered views using EJS templates. 
    Organized by user role with separate view directories for admin, staff (instructors), and students. 
    This layer provides a lightweight web interface for rapid prototyping and testing, though production 
    deployments may use a separate frontend framework.
\end{itemize}

\subsection{Microservice organization}
\subsubsection{Service Decomposition Strategy}
The Microservice implementation decomposes the monolithic application into six independent services, 
each aligned with a functional subsystem defined in chapter 3 and also implemented following Repository pattern.

\begin{itemize}
    \item \textbf{Account Service}: Manages user authentication, role assignment, and session management. 
    Corresponds to the "Account \& Security" subsystem. Provides JWT token generation, 
    password hashing/validation, and role-based authorization. Exposes REST APIs for registration, 
    login, logout, and password recovery workflows.
    
    \item \textbf{Academic Service}: The service handles user profile management and student-instructor assignments, 
    manages student enrollments, instructor-course associations, and department head approvals. Also, the service Implements business rules for 
    enrollment validation and progress tracking.
    
    \item \textbf{Course Service}: Manages course lifecycle, lesson content, and learning materials. 
    Corresponds to the "Curriculum and Instruction" subsystem . Handles course creation, 
    content uploads, category organization, and status transitions (Draft → Published → Closed). 
    Stores course metadata and coordinates with Academic Service for enrollment verification.
    
    \item \textbf{Grading Service}: Implements assessment logic, quiz management, and submission 
    grading. Corresponds to the "Learning \& Assessment" subsystem . Currently under 
    active development to support configurable grading schemes . Will expose 
    APIs for quiz creation, auto-grading, manual scoring, and regrade request workflows.
    
    \item \textbf{API gateway}: Defines NGINX service that unified entry point for all frontend 
    client requests. It functions as a reverse proxy, seamlessly routing incoming traffic to the appropriate 
    backend Microservice (like course-service or academic-service) based on the requested URL path, while completely 
    abstracting away internal port mappings and network complexities from the user.

    \item \textbf{Frontend Gateway}: As a React-based application built with Vite, service
    provides the user interface for all stakeholder groups (students, instructors, administrators)
    and communicates with backend services via REST APIs routed through the Nginx API Gateway. 
    
    \item \textbf{Message Broker (RabbitMQ)}: Facilitates asynchronous communication between services 
    using publish-subscribe and work queue patterns. Decouples service dependencies for operations 
    such as sending enrollment confirmation emails, triggering analytics updates after submissions, 
    or propagating course status changes. Ensures eventual consistency across distributed data stores.
\end{itemize}

\subsubsection{Inter-Service Communication}

Services communicate through two primary mechanisms:

\begin{itemize}
    \item \textbf{Synchronous REST APIs}: For operations requiring immediate responses, such as 
    enrollment validation (Academic Service queries Course Service to verify course status) or 
    authentication (all services validate JWT tokens with Account Service). REST calls introduce 
    network latency but provide strong consistency guarantees.
    
    \item \textbf{Asynchronous Messaging (RabbitMQ)}: For operations tolerating eventual consistency, 
    such as updating progress statistics after lesson completion or sending grade notifications after 
    instructor scoring. Message queues decouple services temporally, allowing producers to continue 
    processing while consumers handle messages asynchronously.
\end{itemize}

Also, services are containerized using Docker and orchestrated via Docker Compose. Each service 
runs in an isolated container with defined resource limits (CPU, memory), network configuration, 
and dependency specifications. This containerization strategy enables:

\begin{itemize}
    \item \textbf{Independent:} Services can be updated, scaled, or rolled back independently 
    without affecting other components, supporting the evolvability evaluation in Change Scenarios.
    
    \item \textbf{Environment Consistency}: Development, testing, and production environments use 
    identical container images, eliminating "works on my machine" discrepancies.
    
    \item \textbf{Horizontal Scaling}: Individual services experiencing high load (e.g., Course Service 
    during enrollment periods) can be scaled by launching additional container instances behind the 
    Nginx load balancer.
\end{itemize}

The Docker Compose configuration defines service dependencies (e.g., Account Service depends on 
PostgreSQL(Docker containerized) and RabbitMQ), startup ordering, and inter-container networking via a private bridge network.

This hybrid approach balances consistency requirements with system resilience—critical operations 
use synchronous calls for immediate validation, while non-critical workflows leverage asynchronous 
messaging to prevent cascading failures.

\section{Architectural Decomposition Strategy}

This section delineates the methodology employed to translate the complex business requirements of a Learning Management System into a structured technical topology. By leveraging Domain-Driven Design (DDD) principles, the study identifies logical boundaries—or "Bounded Contexts"—that remain consistent across both architectural candidates. This strategic decomposition ensures that the subsequent performance comparison is not skewed by varying degrees of functional cohesion, but rather reflects the inherent characteristics of the underlying deployment model.

A pivotal aspect of this research is the strategy used to decompose the LMS business logic into technical components. This study employs Domain-Driven Design (DDD) principles to identify 'Bounded Contexts', ensuring that each module—whether in a Monolithic or Microservice structure—maintains high cohesion.

\subsection{Monolithic Structural Cohesion}
In the Monolithic implementation, the architectural integrity is maintained through Logical Modularization, where bounded contexts are decoupled at the package and directory level rather than through physical service boundaries. This approach aims to achieve high functional cohesion while intentionally retaining a unified execution context.

\textbf{Internal Dependency Management and the "Spaghetti" Risk:}
The primary technical challenge within this model is the mitigation of "spaghetti dependencies"—a state where circular imports and cross-module couplings bypass formal interfaces. To prevent this, the project enforces strict coding conventions and NestJS-specific encapsulation techniques, such as using private providers and exporting only essential services through dedicated module definitions. By treating each folder as a "black box" that interacts with others only via well-defined internal APIs (Service-to-Service calls within the same process), the system maintains a clean separation of concerns. This allows developers to reason about the \textit{Assessment} logic independently of the \textit{User Management} logic, even though they exist within the same codebase.
\textbf{Memory Space and Execution Efficiency:}
One of the most significant advantages of this cohesive structure is the elimination of the "Network Tax." Since all modules share the same memory space, data exchange occurs through memory pointers rather than expensive I/O operations. There is no requirement for JSON serialization, HTTP header processing, or network packet transmission between modules. In the context of an LMS, where a single student request might trigger multiple internal lookups (e.g., checking enrollment status, fetching course content, and logging activity), the monolithic structure provides near-zero latency for cross-module communication. This efficiency is particularly evident during the "Steady-state" operations observed in our benchmarks.

\textbf{The Bottleneck of Shared Infrastructure:}
However, the consolidation of resources introduces a critical vulnerability: Shared Resource Contention. While logical separation is maintained at the code level, it collapses at the infrastructure level. All modules must share a single PostgreSQL database schema and, more importantly, a single database connection pool. During peak student activity—such as the "Flash Crowd" scenario where thousands of students attempt to enroll simultaneously—the database connection pool becomes a global bottleneck.

A high-intensity write operation in the \textit{Enrollment} module can exhaust all available connections, effectively starving the \textit{Course Browsing} module of database access, despite the latter being a lightweight read operation. Furthermore, because the entire application runs within a single Node.js event loop, a CPU-intensive task in one module (such as generating a complex PDF certificate) can block the execution thread for all other modules. This lack of Fault and Performance Isolation is the fundamental trade-off of the monolithic design; the simplicity of deployment and the speed of internal communication are gained at the expense of granular scalability and systemic resilience.

\textbf{Deployment and Lifecycle Simplicity:}
Despite these contention risks, the structural cohesion of the Monolith significantly streamlines the Continuous Integration and Deployment (CI/CD) pipeline. A single build artifact, a single Docker image, and a unified environment configuration mean that the "Environmental Parity" is easier to maintain. For small to medium-sized educational institutions, this reduces the operational burden, as there is no need for complex service meshes, distributed tracing, or coordinated release cycles across multiple repositories. The monolith remains a "single source of truth" for both data and execution logic.

\subsection{Microservice Granularity and Isolation}
The Microservice implementation of the LMS transcends mere code separation, establishing a distributed ecosystem defined by Physical Decoupling and Data Sovereignty. This strategy shifts the focus from structural cohesion within a process to the operational autonomy of independent service units.

\textbf{The Database-per-Service Pattern and Schema Isolation:}
At the core of this isolation is the "Database-per-Service" architectural pattern. Unlike the Monolithic model where a shared schema creates a "Hidden Coupling" at the data layer, each microservice (e.g., \textit{AccountService}, \textit{AcademicService}, \textit{CourseService}) manages its own dedicated PostgreSQL instance. This ensures that the internal data structures of a service are completely encapsulated. For instance, a schema migration or a database engine upgrade within the \textit{Assessment} module can be executed independently without the risk of breaking foreign key constraints or triggering deadlocks in the \textit{Enrollment} logic. This isolation eliminates "Side-Effect Deployments," where a change in one domain unexpectedly cripples another due to shared table dependencies.

\textbf{Communication Dichotomy: Synchronous vs. Asynchronous:}
To bridge these isolated data silos, the architecture employs a sophisticated communication strategy designed to balance Immediate Consistency with Systemic Resilience:

\begin{itemize}
\item \textbf{Synchronous Orchestration via REST:} For operations requiring instantaneous confirmation—such as user authentication at the \textit{AccountService} or real-time grade lookups—the system utilizes synchronous RESTful APIs. While this introduces a direct temporal coupling (the caller must wait for the callee), it ensures that the student receives immediate feedback for critical transactions. However, this study recognizes that an excessive reliance on synchronous calls can lead to "Distributed Monolith" symptoms, where a failure in a downstream service causes a cascading timeout across the entire chain.

\item \textbf{Asynchronous Choreography via RabbitMQ:} To mitigate the risks of synchronous coupling, the system leverages \textbf{RabbitMQ} for non-blocking inter-service communication. When a student enrolls in a course, the \textit{EnrollmentService} publishes an integration event (e.g., \texttt{StudentEnrolledEvent}) to the message broker. Interested services, such as \textit{NotificationService} or \textit{AnalyticsService}, consume this event asynchronously. This "Fire-and-Forget" pattern provides a buffer against traffic spikes; if the \textit{AnalyticsService} is temporarily overwhelmed or offline, the message remains safely in the queue, ensuring eventual consistency without degrading the primary enrollment experience.
\end{itemize}

\textbf{Fault Isolation and the "Blast Radius":}
The granular nature of this architecture fundamentally alters the system's "Blast Radius." In our 2,000 VU stress tests, we observed that resource exhaustion in the \textit{CourseService}—caused by heavy browsing activity—did not impede the \textit{AccountService's} ability to authenticate users. Each service operates within its own set of Docker-defined resource limits (CPU and Memory), preventing any single "noisy neighbor" from consuming the entire host's capacity. This granular isolation is the primary driver of the Resilience Dividend identified in this study, allowing the LMS to maintain partial availability (e.g., "Students can log in but cannot browse new courses") rather than suffering the total system blackouts typical of monolithic failures.

\textbf{Operational Complexity and the "Coordination Tax":}
However, the benefits of granularity are not without cost. The decomposition introduces a significant Coordination Tax. Developers must manage distributed transactions, handle network partial failures (e.g., implementing retries and circuit breakers), and navigate the complexities of service discovery and distributed logging. The requirement for an API Gateway (Nginx) to route traffic and aggregate responses adds a layer of "Proxy Latency" that is nonexistent in the Monolith. This study evaluates whether this infrastructure overhead—the cost of managing eight independent containers and a message broker—is justified by the superior fault isolation and horizontal scaling potential demonstrated at extreme load levels.

\section{Communication and Integration Patterns}

To facilitate a rigorous comparison, the integration layer of both architectures is designed to handle high-concurrency E-learning scenarios.

\begin{itemize}
\item \textbf{Internal Communication:} In the Microservice version, an \textbf{Nginx API Gateway} acts as the single entry point, handling cross-cutting concerns such as SSL termination and CORS. Interservice communication utilizes \textbf{RabbitMQ} for event-driven tasks (e.g., notifying the Enrollment service when a new Course is published), which reduces direct coupling and enhances the system's fault tolerance.
\item \textbf{Data Consistency Model:} The Monolithic version relies on ACID transactions provided by the shared PostgreSQL instance, ensuring absolute consistency. The Microservice version, however, embraces Eventual Consistency for cross-service operations, using asynchronous events to synchronize state. This distinction is a primary factor in the Resource Utilization Efficiency (RUE) and Latency trade-offs analyzed in subsequent chapters.
\end{itemize}
